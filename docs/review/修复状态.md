## 新发现（本次审核外的新问题，待单独处理）

- **阵营命名空间不一致，导致消费端永远匹配不上**：效果里的 `factionId` 用的是 buff 文本标记 `<$cc.g.*>` 的取值（`rh`/`bs`/`psk`/`R6`/`sp`/`lda`…），而 `characters[].group` 用的是官方 `groupId`（`rhine`/`blacksteel`/`pinus`/`rainbow`…），`sg` 形如 `ussg` 派系在角色表里根本没有 group（属于 `teamId=student`）。`src/core/optimizer.js:210` 的 `x.char?.group === effect.factionId` 因此对 `rh`/`bs`/`R6` 等基本恒为 false，`moodRecovery` 的按阵营计数被低估。需要一张「buff 派系 id ↔ 官方 groupId/teamId」映射表，并在生成阶段落成 `factionGroup` 之类的字段，属跨模块改动，未在本轮处理。
- **线索派系没有任何官方 id 表**：`building_data.json` 里线索派系名只是普通关键词（`<@cc.kw>`），`meetingData` 也不含线索表。因此线索只认编号 `clueNo`（依据《罗德岛基建·会客室》线索 1–7 表），不给 `factionId` 编造别处的值。


## 已知副作用（非错误，但需后续 schema 配合）

- **转化类技能**：`resourceId` 改为产物 Y 之后，消耗品 X 在结构化字段里消失，`per=resourcePoint` 读起来变成自指。建议补 `sourceResourceId` / `sourceResourceName`（全库 6 条）。
- **`professions` 数组暂无消费方**：`src/` 只读角色自身的 `profession`，双职业要在排班生效还需改消费端。
- **`capacityBelow(16)` 边界**：中文「16格以下」含 16，下游若按严格 `<` 消费会漏档。
