# effects schema 口径决策（v2.1）

依据：763 条人工核对结果（[SUMMARY.md](SUMMARY.md)）+ 下游消费方实测（`src/core/optimizer.js`、`scripts/check-effects.mjs`）。

## 关键前提：下游几乎不读这些字段

实测 `src/core/optimizer.js` 只消费 `effect.type`、`effect.value`、`effect.target`（仅用于跳过 `otherFacilities`/`dormitory`）、`effect.per`、`effect.factionId`。

**不读 `unit`，不读 flag 的 value。** 因此下列 1、2 两项调整对运行时零影响，仅是数据自洽性修正。

---

## 决策 1：`unit` 统一用 `percent`，废弃 `probability`

- **现状**：schema 文档写 `workshopByproduct` 应为 `probability`；实际全库 91 条一律 `percent`，`probability` 出现 0 次。
- **决策**：以**数据现状**为准，统一 `percent`；修改 `docs/operator-skill-schema.md`，删掉 `probability` 作为推荐值。
- **理由**：语义等价（概率本就是百分比）；`check-effects.mjs` 的 `KNOWN_UNITS` 两者都接受；无运行时消费方。改文档比改 91 条数据成本低且无风险。

## 决策 2：flag 类 `value` 统一为 `1`

- **现状**：schema 写「flag 类为 1」，但 `control_facCostReset[000]`、`moodRecoveryBlock`、`fixedOrder` 等实际为 `0`。
- **决策**：统一规范化为 `1`。
- **理由**：`0` 与「数值为 0 的有效效果」不可区分，容易在下游被 `if (value)` 吞掉（`dorm_recExcludeOther[000]` 的 `moodRecoveryBlock value=0` 正是此类隐患）。flag 的语义由 `type` 承载，value 不参与计算，置 1 无副作用。

## 决策 3：「为自身」用 `target: self`

- **现状**：`manu_skill_spd1[*]` 等「为自身」记为 `target: room`，全库 `productivity`/`capacity` 的 `target: self` 出现 0 次。
- **决策**：描述明确写「为自身」的，`target` 取 `self`。
- **理由**：`self` 是 schema 已定义值；`room` 会让下游误以为加给整个房间。当前无消费方读该组合，改动安全。

## 决策 4：新增 `branch` 字段承载「分支」，`profession` 只放八职业

- **现状**：「如果训练位干员分支为「驭法铁卫」」等信息只存在于 `condition.text`，全库 `branch` 字段 0 处使用。`profession` 无法容纳「行医」这类分支。
- **决策**：
  - `profession` 仅存八个职业（先锋/近卫/重装/狙击/术师/医疗/辅助/特种）。
  - 分支名存入 `branch`（保留中文原文，如 `"驭法铁卫"`），同时保留 `condition.text` 便于人工核对。
- **遗留**：`branch` 目前是中文名，尚未映射到 `subProfessionId`（原始数据 `character_table.json` 只有英文 id，如 `physician`；仓库内无中文子职业对照表）。**映射表待补**，补齐前 `branch` 仅作人工可读字段，程序不可直接判定。

## 决策 5：`condition.type` 收敛到可计算类型

- **现状**：大量「当 X 进驻在 Y」退化为 `condition.type: "other"`，`char`/`room`/`factionId`/`tagId` 全空，程序无法判定。
- **决策**：凡描述能落到已有类型的一律收敛，优先使用（均已存在）：
  - `withCharInRoom`（`char` + `room`）—「当与 X 进驻同一房间一起工作」
  - `charInRoom`（`char` + `room`）—「如果 X 进驻在 Y」
  - `targetMoodNotFull` / `targetIs` — 宿舍目标条件
  - `recipeMoodCost`（`threshold`）—「加工原始心情消耗为 N 的配方」
  - `trainToLevel`（`level`）—「专精技能至 N 级」
- `other` 仅保留给确实无法结构化的表述，且必须同时写入 `manualReview`。

## 决策 6：会客室线索派系用 `clueNo` 编号，不编造 `factionId`

- **现状**：线索派系名（莱茵生命/喀兰贸易/罗德岛制药…）在原始描述里只是普通关键词 `<@cc.kw>`，**没有** `<$cc.g.*>` 阵营标记；`building_data.json` 的 `meetingData` 也不含线索派系表。因此从数据源拿不到这些派系的 id。
- **决策**：
  - 用《罗德岛基建·会客室》的固定线索编号 `clueNo: 1..7` 作为可计算标识（1 莱茵生命 / 2 企鹅物流 / 3 黑钢 / 4 乌萨斯学生自治团 / 5 格拉斯哥帮 / 6 喀兰贸易 / 7 罗德岛制药）。
  - 中文派系名统一放 `factionName`；`clueNotFaction` 条件同时带 `clueNo`。
  - 「线索板上尚未拥有的 / 已经拥有的」是线索范围，记 `clueTarget: notOwned|owned`，**不得**写进 `factionName`。
  - 「下一次必定获得 X 的线索」记 `guarantee: true`，与「更容易获得」的概率提升区分开。
- **理由**：`clueNo` 是唯一既能人工核对、又能程序判定的字段；凭空给 `factionId` 填别处命名空间的值（如把「喀兰贸易」填成 buff 标记里的 `karlan`，而该标记的释义是「谢拉格」）会造成更隐蔽的错误。

## 决策 7：同一效果的多个触发条件用 `condition` + `condition.extra[]`

- **现状**：「如果会客室内只有自身处于工作状态时，连续消耗超过 16 点心情，下一次必定获得……」这类双条件句，此前只保留一个条件。
- **决策**：主条件放 `condition`（`type`/`threshold`），其余并列条件放 `condition.extra: [{type, ...}]`。
- **理由**：与 `workshop_formula_cost&dorm[000]` 已采用的合并方式一致，避免新增嵌套层级，下游可按需只读主条件。

## 决策 8：效果里的 `factionId` 是标记 id，角色侧落 `characters[].factions`

- **现状**：效果 `factionId` 取描述标记 `<$cc.g.*>`（`rh`/`bs`/`R6`/`ussg`…），角色表的官方字段是 `nationId`/`groupId`/`teamId`（`rhine`/`blacksteel`/`student`…），两套命名**永不可能相等**。旧代码用 `char.group === effect.factionId` 判等，导致按派系计数恒为 0（`ussg`/`lda`/`R6`/`sp` 等全部落空）。
- **决策**：
  - 不在效果侧改 id（它来自官方描述标记，是权威），而是在生成阶段翻译成 `characters[].factions: string[]`，下游用 `factions.includes(effect.factionId)`。
  - 映射表 `scripts/lib/factions.mjs` 逐条给出依据（`group` / `nation` / `team` / `teamId` 前缀 / `isSpChar`）。
  - `karlan` 按 `nationId=kjerag` 匹配：描述里配的中文是「谢拉格」（地区），不是官方 `groupId=karlan`（喀兰贸易）。
  - `Defence`/`Attack`（彩虹小队攻防）官方无字段，按原作 R6S 攻防归属补齐 8 名（防守 5 / 进攻 3），并在表内注明这是**外部常识**而非数据字段；出新彩虹干员不会自动进表。
- **理由**：一处翻译胜过 763 条效果改字段；且角色可能同时属于多个派系（如异格 + 阵营），数组才能表达。
- **验证**：19 个 `$cc.g.*` 标记与原文/官方字段双向零差集；`sp` 与官方 `isSpChar` 全集一致（38 名）；`A1` 5 名含芙蓉。

## 决策 9：分母从句删掉后，必须补 `countScope` / `sourceResourceId` / `min` 三个字段

- **现状**：收敛条件时把「每有 N 点 X」「宿舍内每有 1 名干员」这类分母从句整段删除，`per`/`perValue` 保留了，但**计数域**（在哪个房间数）、**资源来源 id**、**数值下限**没有别处承载。
- **实测后果**（第四轮复验发现）：
  - 闪击 `hire_spd_blitz[000]`：情报储备与乌萨斯特饮两条 +5% 删除条件后**完全不可区分**，去重后只剩一条；
  - 三角初华 `control_dorm_bd[000]`：效果在控制中枢、按宿舍人数加热情值，丢了「宿舍内」会被按中枢人数算；
  - 孑 `trade_ord_limit_count[000]`：「订单最少为1」丢失，上限可能被算成 0 或负数；
  - 6 条转化类（感知信息 → 思维链环等）只剩产物、转化率算不出来。
- **决策**：
  - `countScope: { room }` 记计数房间（与效果 `room` 不同时才写）；`{ excludeRooms }` 记排除范围（「宿舍以外」「宿舍和活动室以外」）。
  - `resourceId` 记分母资源；转化类另加 `sourceResourceId` 记被消耗资源。
  - `min` 记下限（订单上限最少为 1）。
  - 同类条件语义要分清：`dormLowMoodCount`（按人数计数）vs `targetMoodBelow`（对目标干员的过滤，每份都加）。
- **理由**：删 condition 的目的只是不让下游把「每 N」误当触发条件，不是丢弃信息；这三类信息必须显式落字段才能保持可计算。
- **补充（第五轮）**：
  - `excludeAssist: true`：原文「基建内（不包含副手及活动室使用者）」的计数限定（副手/活动室未建模，只能标志位），影响 23 条效果；
  - `orderTypeId`/`orderTypeName`：固定获取的订单类型来自 `<$cc.tra.*>` 标记（`pepe` 特别独占订单、`closure` 可露希尔特别订单）；
  - `ignoreOrderEfficiency: true`：佩佩「该类订单不受任何订单获取效率的影响」；
  - `product` 补「赤金订单」→ 贵金属（但书/U-Official/赫德雷等订单类效果，不记会作用到任意订单）。

## 决策 10：心情消耗类默认落在技能持有者本人

- **规则**：`moodCost` / `moodCostReduction` 的效果，若原文没有点名整批目标
  （`全体`、`所有干员`、`房间内所有`、`每名干员的心情`、`X 内干员`），`target` 一律为 `self`。
- **落地**：87 条效果由 `room` 改为 `self`；只有 2 条保持 `room`：
  巫恋「同时全体心情每小时消耗+0.25」、火哨「贸易站内干员心情每小时消耗-0.1」。
- **理由**：「心情每小时消耗+N」消耗的是技能持有者自己的心情；写成 `room` 会被下游摊给同房间所有人，
  把 -0.25 的减免送出去、把 +0.3 的额外消耗强加给队友。

## 决策 11：`target: 'char'` + `char` 表达「点名某个干员」

- **规则**：当原文把加成/消耗明确挂在某个具名干员身上（「丰川祥子的心情每小时恢复+0.1」
  「自身和阿米娅心情每小时恢复+0.05」），用 `target: 'char'` + `char: '<干员名>'` 表达，
  不要退化成 `room`（等于发给全房间）或 `self`（丢掉另一个人）。
- **落地**：`control_dorm_rec2[000]`、`control_mp&meet_spd[000]`、`control_mp_cost_double[000]/[001]`。
- **校验**：`check-effects.mjs` 会拦住 `target: 'char'` 但缺 `char` 的记录。

## 决策 12：配方心情消耗阈值区分「为 N」（精确）与「为 N 以上」（≥）

- **规则**：`condition.recipeMoodCost` 一律带 `op`：`eq`（原文「心情消耗为 N」）或 `gte`（「为 N 以上」）；
  效果级阈值字段相应分成 `recipeMoodCostExact` / `recipeMoodCostAtLeast`。
- **落地**：15 条 `eq`（`workshop_formula_cost3[*]`、`cost5[100]` 等）改用 `recipeMoodCostExact`，
  9 条 `gte` 保留 `recipeMoodCostAtLeast`。
- **理由**：`AtLeast` 读作 ≥ 会把 4/8 心情的配方一并纳入「-2 消耗」，与原文「为 4」不符。

## 决策 13：线索派系只记 `clueNo` + `factionName`（决策 6 的执行）

- **规则**：`clueBias` 不写 `factionId`。`<$cc.g.*>` 是角色表阵营命名空间
  （`karlan`=谢拉格、`rhodes`=罗德岛），与线索 1–7 的派系不是同一套；
  线索派系名在原始数据里只是普通关键词，没有官方 id。
- **落地**：17 条 `meet_*`/`control_clue_faction[*]` 移除 `factionId`；顺带修掉
  「喀兰贸易线索」被标成 `karlan`（谢拉格）、「罗德岛制药线索」被标成 `rhodes` 两处错。

## 决策 14：`per: 'hireSlot'` 指「不包含初始招募位」的招募位

- **规则**：文中「每个招募位（不包含初始招募位）」一律记 `per: 'hireSlot'`，
  该枚举值本身即定义为非初始招募位；下游不得再加 1。
- **落地**：15 条人力办公室效果。

## 决策 15：「每有 N 名 X」从句内的所有效果都按同一计数叠加

- **规则**：`每有 1 名 … 干员（最多 3 名），A +2%，B -0.15」这类句子，从句管辖的是整句，
  因此 A 与 B 都带 `per`/`perValue`/`cap`，不做「第一个叠加、第二个固定」的区分。
- **落地**：杏仁 `manu_formula_spd&cost_bd[000]`（生产力 +2%/人、心情 -0.15/人，cap 3）、
  歌蕾蒂娅 `control_mp_aegir2[*]` 等同型句式。
- **残余风险**：原文没有明说「每名都减心情」，若实测口径是固定值，只需把该条效果的
  `per`/`perValue`/`cap` 去掉即可，不涉及解析器改动。
