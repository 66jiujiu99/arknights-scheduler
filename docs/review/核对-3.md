## 一、系统性问题（同类错误反复出现）

### S1「每个发电站」未被识别为 per=powerStation，落到兜底 per=efficiency
`manu_prod_spd&power[000]/[010]/[020]`：描述「每个**发电站**为当前制造站+X%生产力」，per 应为 `powerStation`（schema 已列出该取值，但全库 0 处使用），实际落为 `efficiency`（effects.mjs 的 PER_RULES 未收录「发电站」，命中兜底规则 `/生产力|效率/ → efficiency`）。
对照：同类句式「每个**贸易站**」已正确解析为 `per=tradingStation`（#41/#42）。→ 影响 #38 #39 #40。

### S2「每级」未生成 per=roomLevel，加成被当成一次性固定值
「训练室每级+X%」（#5）、「当前贸易站每级+1个订单上限」（#64 #65）中的「每级」未转成 `per=roomLevel`（对照「每间宿舍每级+1%获取效率」已正确带 `per=roomLevel`）。→ 影响 #5 #64 #65。

### S3 condition 挂到相邻（无条件）effect 上
- #25：「生产力+5%」是无条件基础值，却被挂上「每有1个木天蓼」条件（该条件只属于 +1% 那条）。
- #71 #72：「订单获取效率+25%/+30%」是无条件基础值，却被挂上「当伊内丝入驻工作场所」条件（该条件只属于额外 +5% 那条）。
→ 影响 #25 #71 #72。

### S4「最多/上限」被拆成一条独立的带 value 的 effect，存在重复累加风险
#7（槐琥）产出 3 条 effect，其中第三条 `{value:40, cap:40, unit:percent}` 把「最多提供40%」的上限写成了一条 +40% 生产力。对照同类贸易站技能 `trade_ord_spd_variable2[000]`（雪雉）只产出 2 条、cap 挂在 value=5 那条上，制造站这条多出一条。→ 影响 #7。

### S5「为自身」一律记为 target=room，与 schema 的 self 取值不一致
#22 #44 #45 #46 #47 描述均含「为自身+…」，但 target 全为 `room`（全库 productivity/capacity 类 target=self 出现 0 次，而 moodCost 类有 17 次用 self）。是否等价取决于排班计算口径（房间总产出 vs 该干员自身贡献），故这 5 条判**存疑**，建议统一口径。→ 见 #22 #44 #45 #46 #47。

### S6 特殊资源 effect 的标识缺失/冲突（非必核字段，但影响可用性）
- 缺 `resourceId`/`resourceName`：#4（心情落差）、#51/#52（人间烟火）、#25（木天蓼）只靠 condition.text 文本表达资源名。
- 转化类产出与来源共用同一 resourceId：#74 黑键「感知信息→无声共鸣」，产出「无声共鸣」误用来源 id `bd_a1`，而 #76/#77 的「无声共鸣」用 `bd_B`，同一资源两个 id。
- 注：转化类 `resourceName` 取产物（Y）的规则本身遵守正确（#74 取「无声共鸣」而非「感知信息」）。

### S7「当与XX在同一个房间」条件类型记为 other，未用 schema 的 withCharInRoom
#2 #3 #59 #60 #61 #62 的 condition.type 为 `other`（仅靠 text），而 schema 与全库已有 `withCharInRoom`（24 处）并列有 `char` 字段。语义未丢失但结构化程度不一致。

### S8 flag 类 effect 的 value 与 schema 文档不一致
schema 称「flag 类为 1」，实际 `fixedOrder`/`resetOthers`/`moodCostReset` 均为 `value:0`（全库 13 处）。属文档与数据口径不一致，建议统一（未据此判错）。→ 涉及 #43 #55 #56 #73 等。

### S9 per=skillClass 未记录技能类名
#45 #46 #47 #44 只写 `per:skillClass`，无字段区分「标准化/莱茵科技/金属工艺」，只能靠 text 区分，排班无法程序化匹配技能类。
