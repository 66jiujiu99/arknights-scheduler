## 系统性问题

### 问题 1（严重，影响 28 条）：基础 +30% 效果被错误挂上「额外加成」的条件

句式统一为：

> 进驻训练室协助位时，「X」干员的专精技能训练速度**+30%**，**如果……，则训练速度额外+Y%**

中文语义是：**+30% 无条件生效**（只要受训干员是该职业/该训练室），**「如果…」只限定后半句的额外 +Y%**。
但解析结果把 `condition`（`trainToLevel` / `other` 分支条件）同时挂到了**基础 +30% 那一条 effect** 上，导致基础加成被误判为"仅在满足条件时才生效"，会**严重低估**训练速度（例如训练至 2 级时该干员的 +30% 会被判为不生效）。

- 影响条数：**28 条**（20 条 `trainToLevel` 型 + 8 条分支 `other` 型）
- 应为：第 1 条 effect（value 30）**不带 condition**；仅第 2 条 effect（value 45/50/65）带 `condition`
- 实为：两条 effect 都带了同一个 `condition`
- 备注：额外加成条（45/50/65）本身**未带 `profession` 限定**，实际游戏中额外加成同样只对"X职业"生效，建议补上 `profession`（本次不单独计为错误，仅提示）

涉及 buffId：
`train_spd&profession2[110]`、`[111]`→实际是 `[112]`、`[120]`、`[130]`、`[150]`、`[180]`、`[220]`、`[230]`、`[240]`、`[250]`、`[270]`、`[320]`、`[322]`、`[440]`、`[620]`、`[630]`、`[640]`、`[650]`、`[660]`、`[680]`、`profession3[131]`、`[140]`、`[151]`、`[161]`、`[170]`、`[181]`、`[183]`、`[191]`

### 问题 2（8 条）：分支限定只落在 condition.text，无结构化字段

`train_spd&profession3[13x/14x/15x/16x/17x/18x/19x]` 的"如果训练位干员分支为「驭法铁卫/速射手/斗士/领主/攻城手/行医/链愈师/游击手」，则额外+45%"：
全库检索确认 **没有任何 effect 使用 `branch` 或 `condition.branch` 字段**（0 处），分支名只存在于 `condition.text` 自由文本里，程序无法据此判断分支。属于全库建模缺口，建议后续统一加 `condition.branch`。本次按"与现有约定一致"处理，仅在"问题 1"里计错误，未重复计。

### 问题 3（5+1 条）：clueBias 的 faction 填了非阵营的占位串

`meet_spd_notOwned[000~004]`、`[010]` 的"更容易获得线索板上尚未拥有的线索"，`faction` 被填成 `"线索板上尚未拥有的"`（一句中文片段，不是阵营名）。语义上是"未持有线索优先"机制而非阵营倾向，且原文并无"工作时长影响概率"却挂了 `condition.type = workTimeAffectsProbability`。计为**存疑**，建议改成专门的 type 或 `condition.type` 标记。

### 问题 4（数据约定观察，不计错）：clueBias 用 `faction` 而非 `factionId`

schema 写的是 `factionId`，但全库 34 处 clueBias 全部用 `faction`（阵营中文名）、40 处用 `factionId`（触发主体筛选）。两种并存且 clueBias 一侧稳定用 `faction`，属既有约定，本批 `meet_flag[010/040/050/060/070]` 按此判定为正确。
